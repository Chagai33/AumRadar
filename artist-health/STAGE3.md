## 1. המטרה (במשפט)
Bootstrap כבר נתן לכל אמן **RANK** (כמה מהמוזיקה שלו בקוראציה שלך, משוקלל-דעיכה). שלב 3 בונה
את השכבה שמעליו: **(א)** לראות *למה* לכל אמן (ממה הציון מורכב), **(ב)** לגרור כפתורים ולראות
את המועמדים משתנים **חי**, **(ג)** להגן ידנית על אמנים (מועדף/נעילה/רצפה), **(ד)** ללחוץ "החל"
שיכתוב את רשימת המועמדים ל-`/cleanup`.

## 2. מה כבר קיים (הבסיס שעליו בונים)
- **`cache/bootstrap_scores.json`** — כל 3,828 העוקבים עם `{artist_uri, artist, rank, entered}`, ממוין.
- **`cache/cleanup_candidates.json`** — הרשימה ש-`/cleanup` קורא (חוזה `Candidate` ב-`Cleanup.tsx`).
- **`_score(songs, current_week)`** ב-`backend/core/bootstrap.py` — הפונקציה הטהורה שכבר מחשבת RANK.
  שלב 3 **מכליל** אותה (מוסיף פרמטרים), לא כותב מחדש.
- **`/cleanup`** — עמוד ההסרה הבטוח (live-filter מול העוקבים, resumable, undo, כפתור 🔒 protect).
  **נשאר כמו שהוא**; הדשבורד רק **מזין** אותו.
- **`bootstrap_songs`** (מבנה ה-`songs` הגולמי) — **נזרק כרגע** בסוף `run_bootstrap`. שלב 3א ישמור אותו.

## 3. הפער היחיד שחוסם כוונון-חי — ולמה
כדי לחשב מחדש RANK לכל ערכי-כפתורים **בלי למשוך שוב מספוטיפיי**, צריך את **חומר הגלם**: לכל שיר,
כל השיבוצים שלו (שבוע · סוג · legacy), מקובצים כך שאפשר להריץ את `_score` שוב. **קריטי:** "השיבוץ
החזק ביותר" של שיר **תלוי בכפתורים** (legacy-weekly מול outof-טרי — מי מנצח משתנה עם המשקלים), אז
חייבים לשמור את **כל** השיבוצים, לא רק את החזק שנבחר פעם אחת. → שלב 3א מוסיף ל-Bootstrap שמירת
`cache/bootstrap_songs.json`.

## 4. הארכיטקטורה — 3 שלבי-משנה (כל אחד נפרס ונבדק בנפרד)

### 4א. המנוע (backend בלבד — נבדק במספרים, בלי UI)
1. **Bootstrap שומר את הגלם.** ב-`run_bootstrap`, אחרי `_score`, לשמור
   `cache/bootstrap_songs.json` = מבנה ה-`songs` (per-ISRC: `artist_uris` + `placements`),
   כשכל placement מועשר ב-`playlist_uri` (לפאנל ה"למה" + לינק). **נשמר per-ISRC בלבד — לא קובץ
   שני per-אמן** (היה מכפיל דאטה ועלול להיסתר מסונכרן); האינדקס-per-אמן נבנה **בזיכרון** בזמן
   הטעינה (ראה §10.3). דורש הרצת-Bootstrap אחת נוספת אחרי פריסת 3א כדי לאכלס (ראה cold-start §10.4).
2. **הכללת `_score`.** לחלץ את הקבועים (`HALF_LIFE_WEEKS`, `TYPE_WEIGHT`, `LEGACY_MULT`) לפרמטרים:
   `_score(songs, current_week, half_life, type_weight, legacy_mult)`. ברירות-המחדל = הערכים הנעולים היום.
3. **Endpoint תצוגה-מקדימה** `POST /api/health/preview` — גוף: `{half_life, weekly, outof, legacy,
   other, bands:[b1,b2,b3]}`. מריץ `_score` המוכלל על ה-`songs` שב**זיכרון** (§10.3), ומחזיר
   **מונים בלבד** לכל קבוצה (🔴🟠🟡🟢) + סה"כ מועמדים. חישוב < שנייה. **קריטי [§10.1]:** המונים
   מחושבים על ה-**RANK האפקטיבי** — כלומר `preview` טוען גם את `artist_manual.json` ומחיל את
   השכבה הידנית (מוציא מוגנים, מכניס חסומים, מחיל רצפה), אחרת המונה שתראה ≠ המועמדים שיישלחו ל-apply.
   (ב-3א, לפני שקיימת שכבה ידנית, זה `_score` גולמי; מורחב אוטומטית כשנבנה 3ג.)
4. **Endpoint "למה" per-אמן** `POST /api/health/artist/{uri}` — גוף: המשקלים הנוכחיים (§11.1/§12.6).
   מחזיר לאותו אמן: RANK (גולמי + אפקטיבי), ופירוט התרומות (לכל שיר: השיבוץ החזק שלו → "Week#278 ·
   weekly · גיל 43 → 0.318"), רשימת הפלייליסטים. **נשלף מהאינדקס-per-אמן שבזיכרון (§10.3).**
5. **Endpoint רשימה** `POST /api/health/ranked` — גוף: המשקלים הנוכחיים (§11.1/§12.6) + `offset/limit/band`.
   הרשימה הממוינת, מדופדפת (3,828 שורות — לא שולחים הכל בבת-אחת), עקבית עם הכוונון החי. **POST (לא GET)**
   כדי לשאת את `bands[]` + המשקלים בגוף JSON מסודר.
6. **Endpoint החלה** `POST /api/health/apply` — גוף: הכפתורים + הגבולות + אילו קבוצות נחשבות
   "מועמד". **followed-centric** (§11.2): עובר על מטמון-העוקבים, מחיל את השכבה הידנית כמְשַנֶּה, וכותב
   `cache/cleanup_candidates.json` (חוזה `/cleanup`). **בונה כל שורת `Candidate` בדיוק כמו `_candidate_row`
   הקיים — מיזוג עם `artists_cache.json` לשדות image/genres/followers/artist_id [§13.5]** (אחרת ה-UI נשבר).
   שומר את הכפתורים ב-`cache/health_weights.json`.
7. **Endpoint כתיבת-עקיפות** `POST /api/health/manual` (§11.4) — גוף: `{artist_uri, disposition?,
   score_floor?, pinned_until?, notes?, tags?}`. **כתיבת-מיזוג ממוקדת** (קורא → מעדכן מפתח-אמן אחד → כותב;
   §12.7) ל-`cache/artist_manual.json`.
8. **Endpoint משקלים** `GET /api/health/weights` (§12.3) — מחזיר את `health_weights.json` הפעיל כדי
   שהדשבורד יאתחל את הסליידרים למצב האחרון שהופעל (ברירת-מחדל אם עוד לא הוגדר).

**אימות 3א:** curl ל-preview עם חצי-חיים שונים → המונים זזים באופן צפוי; apply → הקובץ נכתב ו-`/cleanup`
מציג את הרשימה החדשה.

### 4ב. הדשבורד (frontend — המגרש)
עמוד חדש **`/health`** (אייקון 🎛), מנצל את תבניות Recon/Cleanup/Bootstrap:
- **סליידרים:** חצי-חיים (שבועות) · משקל weekly · משקל outof · מכפיל legacy · משקל other ·
  **גבולות הקבוצות** (b1,b2,b3). כל שינוי → קורא `preview` (debounce ~300ms) → המונים מתעדכנים חי.
  אם אי-פעם ירגיש איטי — כפתור **"רענן"** ידני כגיבוי.
- **הקבוצות המדורגות** (🔴🟠🟡🟢) עם מונים חיים וכפתור "בחר את כל הקבוצה" — **בדיוק כמו ה-tiers
  הקיימים ב-`Cleanup.tsx`** (`TIERS`/`tierColor`/`selectTier`), רק לפי RANK. אמן ממוקם/נספר לפי
  ה-RANK ה**אפקטיבי** (עם רצפה/עקיפות), ובשורתו חיווי 🛡️ אם הציון הועלה ידנית (§10.5).
- **פאנל "למה" לכל אמן:** לחיצה → RANK (גולמי + אפקטיבי, `0.02→0.1` אם יש רצפה) + ממה מורכב (שיר-שיר) + הפלייליסטים + תמונה/ז'אנר/עוקבים + לינק ספוטיפיי.
- **מצב cold-start [§10.4]:** אם `bootstrap_songs.json` לא קיים (טרם רצה Bootstrap בגרסה החדשה),
  ה-API מחזיר "אין נתונים" והמסך מציג הודעה בולטת: *"אין נתוני שירים — הרץ 'רענן נתונים' פעם אחת כדי לאפשר כוונון חי."*
- **תור "נעילות שפגו" [§12.5]:** באנר/קבוצה עליונה בולטת — *"N נעילות פגו — לבדוק מחדש"* — כדי שאמנים
  שה-`pinned_until` שלהם עבר לא ייבלעו ברשימה הרגילה אלא יקבלו תשומת-לב יזומה.
- **כפתור "החל"** → `apply` → מזין את `/cleanup` → לינק "עבור ל-Cleanup". אזהרה-רכה אם קיים manifest-ניקוי פעיל טרי (§11.5).

**אימות 3ב:** גרירת סליידר מזיזה מונים תוך שבריר-שנייה; פאנל ה"למה" תואם את המספרים; "החל" מעדכן את /cleanup.

### 4ג. השכבה הידנית העשירה (העקיפות שלך, גוברות על הציון)
אחסון: `cache/artist_manual.json` = `{artist_uri: {disposition, score_floor, pinned_until,
notes, tags:[]}}` (JSON, בלי SQLite — עקבי עם v1; SQLite עדיין נדחה לשלב 4).
- **`disposition` — כוונה אבסולוטית אחת ובלעדית** (`protect | remove | none`), כדי שלא ייתכן
  קונפליקט "מועדף וגם חסום" [§10.2]:
  - `protect` (מועדף): לעולם לא מועמד, גם אם RANK נמוך. יכול להציע אוטומטית נעילה/רצפה.
  - `remove` (חסימה): תמיד מועמד. **אינו מוחק לבד** — רק מכניס לרשימת /cleanup, שם אתה מאשר ידנית.
  - `none`: הציון האלגוריתמי בלבד.
- **שדות אורתוגונליים (עצמאיים, לא בלעדיים):** `score_floor` (מספר: RANK אפקטיבי = max(מחושב, רצפה);
  מגן בלבד, לא מזייף — §10.5. **אבל `disposition:remove` דורס את הרצפה — §12.4**) · `pinned_until` (נעילה
  עד תאריך; בפקיעה → תור "היה נעול עד [תאריך] — לבדוק מחדש", מוצג ב-§4ב) · `notes` · `tags`. אמן יכול
  להיות `protect` **וגם** עם הערות/תגיות/רצפה.
- **עיקרון-על (מ-DESIGN):** הדשבורד תמיד מציג את הציון האלגוריתמי **ליד** העקיפה — לא דורס את האמת.
- **ריפוי-עצמי [§11.2, מחודד ב-§12.2 = soft-prune]:** **מתעלמים בזיכרון** מרשומות של אמנים שכבר לא
  עוקבים אחריהם (שלא יופיעו/ישפיעו), אבל **לעולם לא מוחקים אותן פיזית** מה-JSON אוטומטית (blip זמני ב-follow
  API שיחזיר רשימה ריקה היה מוחק את כל העקיפות שלך). מחיקה פיזית = ידנית / שלב 4. **אין** צימוד "מחיקה ב-/cleanup → מחיקת רשומה".
- **הגירה + מקור-אמת אחד [§11.3]:** `cache/cleanup/protected.json` (כפתור 🔒) מהוגר פנימה כ-`disposition:'protect'`
  (גיבוי לפני), **ו-`cleanup.py` מעודכן לעבוד בלעדית מול `artist_manual.json`** (`_load_protected`/
  `get_candidates`/`/cleanup/protect`); `protected.json` נמחק אחרי ההגירה. `apply` מכבד את `artist_manual.json`.
- **`get_candidates` מסנן חי מול השכבה הידנית [§13.1]:** מוציא protected/pinned **בזמן-קריאה** (כמו
  שהוא כבר מסנן חי מול העוקבים) → מועדף שסימנת בדשבורד משתקף מיד ב-/cleanup **בלי Apply**. אין "רוחות רפאים".
- **כתיבה בטוחה משותפת [§13.4]:** גם `/cleanup/protect` וגם `/api/health/manual` כותבים דרך מודול
  `manual_store` **יחיד** (read-merge-write ממוקד), כדי ששניהם לא ידרסו זה את זה.

**אימות 3ג:** סימון "מועדף" מוריד אמן RANK-נמוך מהמועמדים; נעילה-עד-תאריך פוקעת לתור-בדיקה; חסימה מכניסה בכוח.

## 7. החלטות שכבר נעולות ✅
1. **קבוצות מדורגות** (🔴🟠🟡🟢 לפי RANK), לא קו-בינארי יחיד. כפתור בחירה per-קבוצה.
2. **חישוב חי בשרת** (recompute < שנייה), עם כפתור "רענן" כגיבוי.
3. **שכבה ידנית מלאה** (מועדף/נעילה-עם-תאריך/רצפה/חסימה) — נכללת בתוכנית, נבנית ב-3ג.
4. **3 שלבי-משנה** נפרסים בנפרד; הארכיטקטורה נעולה עכשיו, המספרים "תחליט חי".
5. **מזין את `/cleanup` הקיים**, לא בונה UI-מחיקה מחדש. **לעולם לא מוחק אוטומטית.**
6. **בלי SQLite** ב-v1 (JSON), עקבי עם Bootstrap. **[נפתח מחדש ואושר בסבב 1]:** ה-DB **מתוכנן במלואו** (סכימת 11 הטבלאות ב-`DESIGN.md`) אבל **נבנה בשלב 4** — שם קיים הדאטה שהוא נועד לו (`release_events` שמצטבר שבועית). בשלב 3 אין דאטה מצטבר: הכל מחושב-מחדש מצילום-מצב → JSON הוא הכלי הנכון, ו-`_score` לא תלוי-אחסון אז אין עבודה כפולה. "לתכנן הכל" ✅ ≠ "לבנות הכל בבת-אחת".

## 8. הכרעות סבב-ביקורת 1 ✅ (היו פתוחות — נסגרו 2026-08-08)
1. **גבולות הקבוצות — ברירת-מחדל 0.05 ו-0.5** (🔴=0 · 🟠 0–0.05 · 🟡 0.05–0.5 · 🟢 0.5+). נקודת-פתיחה בלבד; משתנה בסליידר.
2. **preview מחזיר מונים בלבד** (חי); הרשימה המפורטת נטענת ב**דפדוף** (endpoint `ranked`). לא שולחים 3,828 שורות לדפדפן.
3. **מגרים את `protected.json` → `artist_manual.json`** (ה-🔒 הישן = "נעול לתמיד", תת-מקרה). שכבה אחת. גיבוי לפני ההמרה.
4. **עמוד `/health` נפרד** (לא בתוך `/bootstrap`). Bootstrap = "בנה ציונים" (כבד, חד-פעמי); Health = "שחק ותכוונן" (יומיומי).
5. **רצפת-ניקוד = מגינה בלבד** (לא הופך למועמד), אבל הדשבורד מציג לצידה את הציון **האמיתי**. לא מזייפים את המספר.
6. **`apply` מגבה אוטומטית** את `cleanup_candidates.json` (עם תאריך) לפני כל דריסה, ושומר את הכפתורים ב-`health_weights.json`.
7. **`bootstrap_songs.json` שומר `playlist_uri`** בכל placement → פאנל ה"למה" מראה ומקשר את הפלייליסט המדויק.
8. **ריענון נתונים = כפתור ידני** ("רענן נתונים" מריץ Bootstrap מחדש). ריענון-אוטומטי + צבירה שבועית = **שלב 4** (אותו ממד "קדימה/מצטבר" כמו ה-DB).

## 9. סדר בנייה מוצע (אחרי הנעילה)
3א (מנוע+preview+apply, נבדק ב-curl) → נפרס+מאומת → 3ב (דשבורד) → נפרס+מאומת → 3ג (שכבה ידנית) → נפרס+מאומת.

## 10. הכרעות סבב-ביקורת 2 ✅ — מצבי-קצה, קונפליקטים, ביצועים (נסגרו 2026-08-08)
> חמישה ממצאים מביקורת חיצונית. כולם **עידונים לוגיים**, לא שינויי ארכיטקטורה. עם הנימוק לכל אחד.

1. **preview חייב לכלול את השכבה הידנית — מונים = RANK אפקטיבי.**
   *הבעיה:* אם `preview` מריץ `_score` גולמי אבל `apply` מוציא מוגנים/מכניס חסומים — המונה בזמן
   הכוונון ≠ מה שיינחת ב-/cleanup. *ההכרעה:* `preview` טוען גם את `artist_manual.json` ומחשב מונים
   על ה-RANK האפקטיבי. *(סדר בנייה: ב-3א גולמי, מורחב ב-3ג כשהשכבה קיימת.)*

2. **קונפליקט מועדף/חסום — `disposition` בלעדי, והגנה גוברת.**
   *הבעיה:* מבנה של בוליאנים נפרדים אִפשר "מועדף וגם חסום" בלי מנצח מוגדר. *ההכרעה:* כוונה אבסולוטית
   אחת ובלעדית (`protect|remove|none`) — הקונפליקט נמנע מלכתחילה ב-UI. אם בכל-זאת יתנגשו (מיגרציה/באג)
   → **הגנה גוברת. הנימוק:** כל הפרויקט בנוי על בטיחות והגנת-מועדפים; מחיר "שמרתי בטעות" זניח, מחיר
   "סימנתי מועדף למחיקה" כואב. `remove` בלאו-הכי לא מוחק לבד (רק מכניס ל-/cleanup, שם מאשרים ידנית).
   `score_floor`/`notes`/`tags` נשארים אורתוגונליים (לא בלעדיים).

3. **ביצועים — `songs` בזיכרון-התהליך + אינדקס-per-אמן בזיכרון (לא קובץ שני).**
   *הבעיה שהוצעה:* סריקת ~8,285 שירים למצוא אמן. *הערכה אמיתית:* סריקה כזאת = ~1-2ms, זניחה
   (לוחצים אמן אחד בכל פעם). הפינה ה**אמיתית**: להוריד קובץ 3-5MB מ-GCS ב**כל גרירת-סליידר**. *ההכרעה:*
   לשמור את `songs` ב**זיכרון-התהליך** (נטען פעם אחת), ובאותו מעבר לבנות אינדקס-per-אמן בזיכרון —
   כך גם preview וגם פאנל ה"למה" מיידיים, **בלי קובץ per-אמן כפול** (שהיה עלול להיסתר מסונכרן).

4. **Cold-start — לפני הריצה הראשונה בגרסה החדשה.**
   *הבעיה:* עם פריסת 3א, `bootstrap_songs.json` עוד לא קיים (ה-Bootstrap הישן לא ייצר אותו). *ההכרעה:*
   (א) 3א כולל **הרצת-Bootstrap אחת** אחרי הפריסה לאכלוס; (ב) הדשבורד מטפל בחן בהיעדר — API מחזיר
   "אין נתונים", המסך מציג *"הרץ 'רענן נתונים' פעם אחת"*. (בדיוק סוג ה-edge-case של ה-scope שנשך ב-Bootstrap.)

5. **RANK אפקטיבי מול גולמי — מיקום ומונים לפי האפקטיבי, מציגים את שניהם.**
   *הבעיה:* אם גולמי=0.02 (🔴) ורצפה=0.1 (🟡) — באיזו קבוצה האמן? *ההכרעה:* למיקום ולמונים — לפי
   ה**אפקטיבי** (🟡, כדי שתדע שהוא בטוח); בשורת-האמן חיווי ברור (🛡️ + `0.02→0.1`) שמזכיר שהציון הועלה
   ידנית ואינו הגולמי. שקיפות בלי זיוף המספר.

## 11. הכרעות סבב-ביקורת 3 ✅ — התפר עם /cleanup, זרימת-נתונים, ריפוי-עצמי (נסגרו 2026-08-08)
> חמישה ממצאים על התפר בין המנוע הדינמי ל-/cleanup הישן. 1/3/4 התקבלו כלשונם; 2/5 בגרסה נכונה יותר
> (ריפוי-עצמי במקום צימוד-שמסתחף; אזהרה-רכה במקום "קריסה") — מבוססת על מנגנונים קיימים בקוד.

1. **משקלים נוסעים עם כל קריאה תלוית-משקלים.** `preview`+`ranked`+`artist` — כולם מקבלים את משקלי
   הסליידרים הנוכחיים ומחשבים מחדש מה-`songs` שבזיכרון. *הנימוק:* אחרת דריל-דאון לקבוצה או פתיחת אמן
   יראו נתונים לפי ברירת-מחדל/apply-קודם — לא עקבי עם מה שאתה רואה במונים בזמן הכוונון. זול (< שנייה).

2. **השכבה הידנית מרפאת-עצמה — לא מצמדים.** *הבעיה:* `disposition:remove` נשאר אחרי ביטול-מעקב מוצלח →
   "רוח רפאים". *הנימוק שממתן:* `/cleanup` כבר עושה live-filter מול העוקבים (נושר מהתצוגה, אין 404),
   ו-`apply` הוא followed-centric (עובר על העוקבים; disposition = מְשַנֶּה) → לא-עוקב לא נכנס מחדש. *ההכרעה:*
   מתייחסים לרשומות רק עבור עוקבים-נוכחיים (**soft-prune — מתעלמים, לא מוחקים פיזית; מחודד ב-§12.2**).
   **נדחה** הפתרון "מחיקה ב-/cleanup תמחק את הרשומה" — הוא מחזיר את סחף-הרישום שכבר תיקנּו (`removed.json`→live-filter) ומפספס ביטול-מעקב שנעשה מחוץ לאפליקציה.

3. **/cleanup עובר למקור-אמת אחד.** משימה מפורשת בבנייה: `cleanup.py` (`_load_protected`/`get_candidates`/
   `/cleanup/protect`) יעבוד **בלעדית** מול `artist_manual.json` (disposition:protect); `protected.json`
   נמחק אחרי ההגירה. *הנימוק:* להשאיר את כפתור ה-🔒 כותב ל-`protected.json` = שני מקורות-אמת שמתפצלים.

4. **endpoint לכתיבת עקיפות** — `POST /api/health/manual` (היה חסר; ראה §4א.7). בלעדיו אין דרך לשמור
   מ-UI את המועדף/רצפה/נעילה.

5. **דריסת cleanup-בתהליך — אזהרה-רכה, לא קריסה.** *הבעיה שהוצעה:* apply דורס את הקובץ בזמן ניקוי פעיל.
   *הנימוק שממתן:* לולאת ה-unfollow ב-`Cleanup.tsx` (`doUnfollow`) רצה על **state בדפדפן** + manifest,
   **לא** קוראת מחדש את `cleanup_candidates.json` → דריסה לא מקריסה; ו-apply כבר מגבה אוטומטית (§8.6).
   *ההכרעה:* ליטוש-UX בלבד — אזהרה-רכה בדשבורד אם קיים manifest-פעיל טרי ("יש תהליך ניקוי פתוח — 'החל' יחליף את הרשימה").

## 12. הכרעות סבב-ביקורת 4 ✅ — cache, בטיחות-דאטה, השלמות-API (נסגרו 2026-08-08)
> 7 ממצאים. 1-6 התקבלו (2 **מתקן טעות שלי מ-§11.2**); 7 מוגזם להקשר משתמש-יחיד → ממוזער.

1. **Cache invalidation ל-`songs` בזיכרון.** Bootstrap רץ כ-Job נפרד וכותב את הקובץ; ה-Service מחזיק
   עותק בזיכרון → מתיישן עד restart, והכוונון החי עובד על דאטה ישן בשקט. *ההכרעה:* טעינה-מחדש לפי
   ה-generation/mtime של `bootstrap_songs.json` (בדיקה זולה ב-preview דרך `storage.get_metadata`;
   מוריד מחדש רק אם השתנה). מטפל גם ב-cold-start (§10.4) באותו מנגנון.
2. **soft-prune — מתקן את §11.2.** הניסוח "גוזמים רשומות" היה מסוכן: מחיקה פיזית לפי רשימת-עוקבים
   שעלולה לחזור ריקה/חלקית זמנית (ה-API מקרטע) → **אובדן בלתי-הפיך** של עקיפות/נעילות/הערות. *התיקון:*
   **soft-prune** — מתעלמים בזיכרון מרשומות של לא-עוקבים (שלא יופיעו), **אף פעם לא מוחקים פיזית** מה-JSON
   אוטומטית. מחיקה פיזית = ידנית / שלב 4.
3. **`GET /api/health/weights`** (§4א.8) — מחזיר את `health_weights.json` הפעיל כדי לאתחל את הסליידרים
   למצב האחרון שהופעל. היה חסר — בלעדיו הדף נטען עם ברירת-מחדל במקום מה שכיווננת.
4. **קדימות `disposition:remove` > `score_floor`.** אם אמן `remove` וגם עם רצפה גבוהה — ה-remove דורס
   (אמרת "הסר" → רצפה לא מצילה, נשאר 🔴). `disposition` היא הכוונה האבסולוטית; הרצפה משפיעה רק כש-`disposition` = none/protect.
5. **תור "נעילות שפגו" ב-UI** (§4ב) — באנר/קבוצה עליונה בולטת "N נעילות פגו — לבדוק מחדש", שאמנים
   שה-`pinned_until` שלהם עבר לא ייבלעו ברשימה הרגילה.
6. **`ranked`+`artist` → POST עם גוף JSON** (כמו preview; §4א.4-5), במקום `bands[]`+עשרוניים ב-query מסורבל.
7. **Race על הקובץ הידני — כותב-יחיד, ממוזער, נדחה.** *מוגזם להקשר:* משתמש-יחיד, וה-DESIGN כבר אימץ
   "כותב-יחיד" (כמו state הסריקה). דורש עריכה בו-זמנית בשני טאבים — הסתברות זניחה, נזק קל והפיך. נעילת-קבצים
   אין ב-GCS בפשטות = הנדסת-יתר. *ההכרעה:* **כתיבת-מיזוג ממוקדת** (קורא → מעדכן מפתח-אמן אחד → כותב;
   `POST /api/health/manual`) שממזערת את החלון; בקרת-מקביליות אמיתית מגיעה עם ה-DB בשלב 4.

## 13. הכרעות סבב-ביקורת 5 ✅ — סנכרון /cleanup, UX, כתיבה בטוחה (נסגרו 2026-08-08)
> 6 ממצאים. 1/3/4 אמיתיים ונכנסו; 5/6 כבר מכוסים בתשתית (מתועדים מפורשות); 2 מבוסס אי-הבנה של GCS (מתוקן).

1. **`get_candidates` מסנן חי מול השכבה הידנית** (§4ג) — מוציא protected/pinned בזמן-קריאה, כך שמועדף
   שסומן בדשבורד משתקף מיד ב-/cleanup בלי Apply. blacklist-add קורה ב-Apply. אין "רוחות רפאים".
2. **קובץ הגלם — GCS אטומי בפרוד (לא סיכון).** `save_json` בפרוד = `upload_from_string` → כתיבת-אובייקט
   אטומית; קורא אף פעם לא מקבל JSON קטוע. הבעיה קיימת רק בכתיבה-מקומית (דב). *תיקון nice-to-have:* כתיבה-מקומית
   אטומית (`.tmp`+`os.replace`) ב-`storage_manager` — שיפור-דב, לא סיכון-פרוד.
3. **`disposition:remove` דורס את המיקום ל-🔴** (מרחיב §12.4). אמן עם RANK גבוה (למשל 0.9/🟢) שסומן remove
   נופל ל-🔴 (מועמד ברור), והציון הגולמי 0.9 מוצג לצידו לשקיפות (עקבי עם §10.5). לא רק "דורס את הרצפה" — דורס את המיקום.
4. **מודול `manual_store` יחיד** (§4ג) — read-merge-write ממוקד ובטוח, משמש גם את `/cleanup/protect` וגם
   את `/api/health/manual`, כדי ששני מקורות-הכתיבה לא ידרסו זה את זה.
5. **Apply ממזג עם `artists_cache.json`** (§4א.6) — לשדות הוויזואליים של חוזה `Candidate` (image/genres/
   followers). **כבר הדפוס של `_candidate_row` הקיים** — מתועד מפורשות, לא פער.
6. **Cold-start לקבצי קונפיג — כבר מטופל.** `storage.load_json(file, default={} / DEFAULTS)` מחזיר default
   כשהקובץ חסר (הדפוס בכל המערכת) → אין קריסה בהרצה ראשונה. רק להקפיד להעביר default נכון.
