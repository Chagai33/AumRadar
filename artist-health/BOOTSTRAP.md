# Bootstrap — שלב 2 — תוכנית מפורטת (לביקורת)

> **סטטוס: נעול (אחרי 4 סבבי ביקורת מבוססי-קוד) — code-ready. כל ההחלטות סגורות (§11).** משלים את `DESIGN.md`.
> נכתב 2026-08-07. המטרה: להפוך את מפת-הפלייליסטים של Recon לנתוני-אמנים אמיתיים —
> RANK per אמן — שמזין את המועמדים למחיקה ב-`/cleanup`.

---

## 1. המטרה (מה Bootstrap עושה, במשפט)
עובר על הפלייליסטים ש**סימנת include** ב-Recon, מושך את הטראקים שלהם, ומחשב לכל אמן
**RANK** = כמה מהמוזיקה שלו נמצאת בקוראציה שלך, משוקלל בדעיכה. **RANK = 0** (אמן שאתה
עוקב אבל אף שיר שלו לא נכנס לשום פלייליסט שנכלל) = מועמד למחיקה. **RANK > 0** = שומרים.

## 2. הקלט
- **הפלייליסטים שנכללו:** מ-`cache/recon_playlists.json` + `cache/recon_inclusions.json`
  (הסנאפשוט של Recon + ה-overrides). כרגע = השבועיים מכל העונות. לכל אחד: `type`,
  `week_number`, `season`, `legacy`.
- **רשימת העוקבים:** `cache/artists_cache.json` (כבר קיים ב-GCS) — כדי לדעת מי מועמד
  (רק אמן שאתה **עוקב** אחריו רלוונטי למחיקה).
- **השבוע הנוכחי:** נקרא חי (מספר-שבוע מקסימלי מהסנאפשוט, או תאריך→שבוע) — עוגן הדעיכה.

## 3. הפלט
1. **DB (SQLite ב-GCS)** — טבלאות ליבה + ציונים (סעיף 6).
2. **`cache/cleanup_candidates.json`** — בפורמט שעמוד `/cleanup` הקיים כבר יודע לקרוא.
   **חובה לכלול `artist_id`** (ה-ID החשוף, לא רק URI) — `cleanup.py` מסנן חי מולו; בלעדיו
   העמוד נכשל [ביקורת סבב 1]. שדות: `artist_uri` · `artist_id` · `artist` · `image` ·
   `genres` · `followers` · `entered` · `tier` · `spotify_url` (**`releases` יורד ב-v1, §9**).
   כך ש**לא בונים UI מחדש** — רק מזינים אותו מהציונים.

## 4. הארכיטקטורה — איפה זה רץ (החלטה מרכזית)
משיכת טראקים ל-~340 שבועיים = ~340 קריאות `GET /playlists/{id}/tracks`. זה **חורג**
מבקשת-web אחת (מגבלת ~26ש' של Netlify). שתי אפשרויות:

| גישה | איך | יתרון | חיסרון |
|------|-----|-------|--------|
| **A. Cloud Run Job** | כמו `aumradar-scan` | רץ שעות ללא מגבלה | **צריך `gcloud run jobs update --image` ידני אחרי כל build** (ה-gotcha הכואב) |
| **B. לולאה-ניתנת-להמשך ב-Service** ⭐ | כמו `/cleanup`: השרת מעבד פרוסה מתוחמת-זמן (<15ש'), שומר checkpoint ב-GCS, מחזיר "כמה נשאר", הפרונט מלולאה עם פס-התקדמות | **נשאר ב-Service — בלי gotcha של Job image.** מנצל תבנית מוכחת | קצת יותר עבודת-פרונט |

**החלטה [ביקורת סבב 2]: A — Cloud Run Job, רץ רצוף.** ל-Job אין "לקוח ממתין", אז על 429 פשוט
`time.sleep` וממשיכים באותה ריצה — **בלי מנגנון chunks/resumable-מול-פרונט** (זה שייך ל-Service).
**התובנה שמפשטת את v1: מדלגים על SQLite לגמרי.** ה-Job מושך טראקים → מצרף RANK **ב-Python** (בזיכרון)
→ פולט `cleanup_candidates.json` דרך `save_json` הקיים. אין SQLite → אין binary-I/O (ש-`storage_manager`
לא תומך), אין בעיית `POWER()`. persistence אמיתי (SQLite) נבנה בשלב 4 כשצוברים `release_events`.
**מנצל את תשתית ה-jobs הקיימת** (`job_trigger.py`/`scan_job.py`, trigger+poll — הטאב יכול להיסגר).
מחיר יחיד: gotcha עדכון-image — **ניתן לאוטומציה** ע"י צעד `gcloud run jobs update` ב-Cloud Build.
(אלטרנטיבה C — לולאת-Service+shards — תקפה אם ה-gotcha dealbreaker, אבל מכריחה טאב-פתוח + קוד-פרונט.)

## 5. שליפת הנתונים — מה ה-API נותן (יתרון חשוב)
`GET /playlists/{id}/tracks` מחזיר לכל טראק אובייקט **מלא**: `id`/`uri`, `name`,
`external_ids.isrc` ✅, `album.album_type` ✅, `artists[]` (עם `id`+`uri` לכל האמנים כולל
פיצ'רינג) ✅, ו-`position` (הסדר). **כלומר ISRC + album_type + כל ה-artist-IDs מגיעים
בקריאה אחת per פלייליסט — בלי קריאות-העשרה נוספות** (בניגוד לפלט הסריקה המצומצם). מדויק, זול.

## 6. מבנה הנתונים ל-v1 — בזיכרון (Python), **בלי SQLite** [סבב 4]
> החלטת §4: v1 מצרף בזיכרון ופולט JSON. SQLite (ב-GCS) **נדחה לשלב 4** — כשצוברים
> `release_events` וצריך persistence. הסכימה המלאה של ה-DB שמורה ב-`DESIGN.md` לשם.

מבני-הזיכרון (נבנים תוך כדי המשיכה, נזרקים בסוף הריצה):
- `songs: dict[isrc] -> {album_type, artist_uris: set, placements: [{week_number, type, legacy}]}`
  — דדופ טבעי לפי ISRC; `placements` = כל הופעה בפלייליסט שנכלל.
- `followed: dict[artist_uri] -> {artist_id, name, image, followers, genres}` — מ-`artists_cache.json`.
- **תוצר:** `scores: dict[artist_uri] -> {rank, entered}` (סעיף 7) → ממנו נגזר ה-JSON.
- ~340 פלייליסטים × עשרות טראקים = עשרות MB ב-RAM — זניח ל-container. **אין טבלאות, אין SQL.**

## 7. נוסחת ה-RANK — משוקללת-דעיכה (הנעולה)
לכל **הופעה** של שיר של אמן בפלייליסט שנכלל:
```
תרומה = משקל_סוג × מכפיל_legacy × 0.5^(גיל / חצי-חיים)
גיל = השבוע_הנוכחי − week_number של הפלייליסט
```
- `משקל_סוג`: weekly = 1.0 · outof = 0.05 · (מועדפים/אחר בעתיד). ⚙️
- `מכפיל_legacy`: 0.5 לפלייליסט legacy (עונה 1), 1.0 לשאר. ⚙️
- `חצי-חיים`: ברירת-מחדל 26 שבועות (~6 ח'). ⚙️
- **דדופ + השיבוץ החזק ביותר:** מקבצים לפי **ISRC**. לשיר שמופיע בכמה פלייליסטים
  שנכללו → לוקחים את ההופעה עם התרומה **הגבוהה ביותר** (לא סוכמים כפילויות-מיון).
- **זיכוי פיצ'רינג:** שיר מזכה את **כל** האמנים שלו (ראשי + משניים), דרך `track_artists`.
- **RANK של אמן** = Σ על השירים הייחודיים (ISRC) שלו, כל אחד בתרומה החזקה שלו.
- **מימוש [סבב 2]:** החישוב **ב-Python בזיכרון** (`0.5**(age/half_life)`), לא ב-SQL — SQLite בלי
  `POWER()` מובנה. (אם אי-פעם נחשב ב-SQL — צריך `con.create_function("pow", 2, math.pow)`.)
- **תמיד ≥ 0, ולעולם לא בדיוק 0 אם הופיע** (דעיכה לא מגיעה לאפס) → **RANK = 0 ⟺ מעולם לא הופיע.**

**דוגמה (חצי-חיים=26, שבוע נוכחי=321):**
- שיר ב-Week#278: גיל 43 → 0.5^(43/26)=0.318 × 1.0 = **0.318**.
- שיר legacy ב-Week#31: גיל 290 → 0.5^(290/26)=0.00044 × 0.5 × 1.0 ≈ **0.0002** (זעיר אבל >0).
- אמן עם שני השירים האלה: RANK ≈ **0.318**. אמן בלי אף הופעה: RANK = **0** → מועמד.

## 8. הצינור (pipeline) — צעד-צעד
1. **טעינה:** קורא את הפלייליסטים שנכללו + רשימת העוקבים. בונה/פותח את ה-DB ב-GCS.
2. **משיכה (Job, רצוף):** לכל פלייליסט → `GET .../tracks` עם **לולאת pagination** (`next`/`offset`,
   **100 טראקים/בקשה** — פלייליסט ארוך = כמה עמודים [סבב 2]). אוסף בזיכרון: ISRC · album_type ·
   כל ה-artist-IDs · position. על 429 → `time.sleep(retry_after)` וממשיכים. checkpoint קליל אופציונלי
   (אילו נמשכו) רק להגנת-קריסה — **לא** לולאה-מול-פרונט. **פלייליסט שנמחק/הפך-פרטי מאז Recon
   → `404`/`403`: try-except שמדלג ומתעד, בלי להקריס את ה-Job [סבב 4].**
3. **חישוב RANK (בזיכרון, לא SQL) [סבב 4]:** אחרי המשיכה — לולאת Python על `followed`, מצרפת
   לכל אמן את השירים שלו עם הדעיכה (§6/§7) → `scores: dict[artist_uri] -> {rank, entered}`.
4. **ייצור מועמדים:** מייצר `cache/cleanup_candidates.json` מהציונים (סעיף 9).

## 9. מ-RANK למועמדי-מחיקה (`/cleanup`)
- **`entered`** (כמה שירים שלך שלו נכנסו) = נגזר ישירות מ-Bootstrap (ספירת ISRC ייחודיים
  שהופיעו). **`RANK`** = הציון המשוקלל.
- **מועמד** = אמן **עוקב** עם **RANK = 0** (`entered = 0`) — אתה עוקב, אבל שום שיר שלו
  לא נכנס לאף פלייליסט שנכלל.
- **מיון/דירוג (tier) — נסגר [ביקורת סבב 1]:** מספר-השחרורים **לא זמין בזול** (`/me/following`
  מחזיר `followers`/`genres`, לא ספירת-שחרורים; זה קריאה per-אמן = אלפי קריאות). ל-v1: **tier לפי
  `followers.total`** (מקונן באובייקט, לא שדה שטוח [סבב 2]; חינם, כבר ב-`artists_cache.json`) או אחיד. הסיגנל "מציף הרבה" מגיע ב**שלב 4**
  (מהסריקה, `release_events`).
- **מוגנים לא נכנסים** (מועדף/נעול/blacklist — השכבה הידנית). **מחיקה = הצע-ואשר תמיד.**

**חוזה-הפלט ל-`cleanup_candidates.json` — קריטי, מונע קריסת ה-UI [ביקורת סבב 3]:**
כל שדה חייב להתאים ל-`interface Candidate` ב-`Cleanup.tsx` (אחרת קריסה/תצוגה שבורה):
- `genres` = **מחרוזת** `", ".join(artist["genres"])` — **לא** מערך (ה-UI עושה `.toLowerCase()` → `TypeError`).
- `releases` = **`0`** (להציב, לא להשמיט — השדה חובה בממשק ומרונדר).
- `followers` = **שטוח** `artist["followers"]["total"]` — לא האובייקט המקונן.
- `artist_id` = ID חשוף (הסינון-החי מולו) · `image` = `images[0]["url"]` · `entered` = ספירת ISRC שנכנסו.
- `tier` — **נסגר: רשימה שטוחה, בלי קיבוץ [החלטת המשתמש].** לא מקבצים לפי עוקבים. מזינים `tier`
  בערך-בודד ניטרלי; המשתמש עובד עם "All"/חיפוש. **אין שינוי ב-`Cleanup.tsx`.**

## 10. עמידות (מנצל תבניות קיימות)
דגל-עצירה מ-GCS · checkpoint-resumable · טיפול-429 עם Retry-After · כתיבת-DB אטומית
(כתוב לקובץ זמני ואז החלף). כולם קיימים בסריקה/ניקוי — Bootstrap מאמץ אותם.

## 11. החלטות — כולן נעולות ✅ [המשתמש, אחרי 4 סבבי ביקורת]
1. **ארכיטקטורה:** A — Cloud Run Job, רץ רצוף, v1 **בזיכרון בלי SQLite** (JSON בלבד).
2. **חצי-חיים = 26 שבועות (~6 ח'); מכפיל-legacy = 0.5** (מכווננים בהמשך ב-preview).
3. **מועמד = RANK=0 בלבד** (אמן שאף שיר שלו מעולם לא נכנס). בלי "נמוך מאוד".
4. **דדופ:** שיר ייחודי לפי ISRC, שיבוץ חזק ביותר.
5. **רשימה שטוחה**, בלי tiers/עוקבים.
6. **מחיקה = ידנית תמיד** ע"י המשתמש ב-/cleanup. Bootstrap רק מכין את הרשימה, **לעולם לא מוחק**.
7. פתרונות טכניים סגורים: pagination · 404/403-skip · POWER→Python · genres→string · followers-flat · artist_id.

## 12. אימות (end-to-end)
- אמן ידוע (למשל אחד שאתה יודע שנכנס הרבה) → RANK גבוה; אמן שאתה יודע שאף פעם לא נכנס → 0.
- מספר המועמדים (RANK=0) סביר ותואם את הפיילוט (~2,400 לא-נכנסו-אף-פעם היה הסדר גודל).
- בדיקת דדופ: שיר שחוזר בכמה שבועיים נספר פעם אחת.
- הרצה חלקית → עצירה → המשך: אין כפילויות, אין דילוגים.
